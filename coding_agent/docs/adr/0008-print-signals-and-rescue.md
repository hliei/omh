# Print 合作信号取消与独立保存救援

状态：已接受，随 14 票实现。

print 进程收到首次 `SIGINT`／`SIGTERM`／`SIGHUP` 时停止接纳和发送余下
prompt，通过 SDK 公开 `abort` 边界合作取消当前活动，等待 Agent／工具／
retry／summary 收束、已有历史保存和普通 close，再分别以 130／143／129 退出。
取消一个 `prompt` 等待者不等于停止它拥有的工作，因此信号路径不取消等待者，
也不在 awaited callback 内等待依赖它返回的 idle／close，不设自动硬超时，也不
回滚已完成副作用。第二次终止信号直接用 `os._exit` 强退，并在 stderr 说明保存
可能不完整；此后不再承诺合作清理或完整保存。

默认自动保存失败时仍退出 1，并把完整内存历史另存到独立的 `omh-rescue-*`
临时目录。成功时 stderr 给出可重开路径，失败时明确说明没有完整保存。救援只写
独立副本：不 rebind 或修复原目标、不把原调用变为成功、不发送额外模型请求。
`--no-session` 不自动救援。永久 stdout 写错误由输出／背压契约直接退出 1，不走
本决定承诺的信号或救援清理。

未采用的选择：

- **取消 `prompt` 等待者并另起收尾**：会让等待者返回而拥有的任务仍在运行，
  与 SDK 的活动所有权冲突，也让已完成副作用的状态不可解释。
- **给合作清理加硬超时**：会中断仍在进行的保存或工具清理，并制造“已完成”
  假象；强退由用户第二次信号显式触发。
- **救援时重写原保存目标**：会把救援伪装成原调用修复，违反两种状态分离。
- **与 EPIPE 直接退出合并**：永久 stdout 失败必须立即退出，等完整保存会改变
  已确认的背压与写失败语义。

代价与边界：首次信号后的退出码固定为 128+signal，即使清理期间保存失败也保留
该码并另行给出救援诊断；救援目录需要临时空间，失败时必须报告没有完整保存；
本决定只覆盖 print 进程信号，interactive 退出与按键取消由各自契约维护。
