# 交互待发队列、撤回与退出保护由产品自持

状态：已接受，随交互 steering／follow-up、撤回与取消票实现。

交互用户需要在模型运行时纠偏或追加任务，能看见并整体撤回尚未消费的输入，
用明确的优先级取消活动，并且在退出时不静默丢失未提交的文字、队列或附件。
SDK 已拥有两个 FIFO 队列及其消费边界（[SDK Agent](../../../docs/agent.md) 的
Input queues），本决定只覆盖产品的接纳、显示、撤回与退出保护，不新增第二个
队列或运行状态机。

决定：

- **接纳**：模型运行中 Enter 走 `AgentSession.steer`，Alt+Enter 走
  `AgentSession.follow_up`，空闲时两者都提交普通 prompt。接纳时即展开 skill／
  template 并按既有 `process_image` 捕获待发图片，与提交 prompt 相同；消费时机
  完全由 SDK 的 drain 边界决定，不抢占已启动的工具批次。被拒绝的接纳（未保存、
  无视觉模型等）把文字与图片放回草稿并给诊断。
- **显示**：每次接纳打印 `queued <kind> (n waiting): <text>` 行；状态行只在
  非零时显示 steering／follow-up 等待数，避免改变既有状态形状。队列内容一律
  通过公开 `AgentSession.queued_messages`（`AgentQueueSnapshot`）读取，不保存
  第二份队列状态；被 SDK 消费的队列消息按普通 `you <text>` 回合显示，消费与否
  以实际消费或显式撤回为准，不从运行结束推断。
- **撤回**：Alt+Up 先全部 steering、再全部 follow-up，以空行并入编辑器，保留
  原草稿；队列图片按发送数据键回到同一待发草稿，保持原 identity。撤回是
  整体操作并显式清空 SDK 队列，不承诺两类交错顺序，也不提供逐条 ID 编辑。
- **取消**：Escape 先关补全；否则撤回队列并通过公开 `abort()` 取消模型，随后
  仍显示 `phase cancel` 且同一会话可用。取消不回滚已执行工具副作用、不跳过
  Agent 清理、也不丢弃未消费队列；取消 host 等待任务不等于活动已停，活动
  收束仍由 Agent 的 abort／settle／close 决定。
- **退出保护**：Ctrl+C 清空编辑器并缓存该行，500ms 内第二次 Ctrl+C 进入退出
  处理；Ctrl+D 只在严格空编辑器时进入。任一方式在仍有未提交文字、待发或处理中
  图片、未消费队列时先要求决定：Enter 明确丢弃并退出 0，其他键返回编辑并恢复
  被清空的行；未提交内容不落盘。操作系统信号不共用此路径，按既有契约合作
  取消、保存并退出 130／143／129。

未采用的选择：

- **产品自建队列与运行状态机**：与 SDK 队列／执行策略重复，两个真源会产生
  消费与显示不一致。
- **用 peek 逐条取出再重排做撤回**：队列快照已隔离，无法在保留 identity 的
  前提下重排；逐条编辑也不是本阶段承诺。
- **取消时静默清空队列**：丢失用户输入，且无法区分“撤回”与“丢弃”。
- **Ctrl+C 双按一律立即退出**：会静默丢弃未提交文字／图片／队列，与退出保护
  目标冲突。
- **进程信号也走退出确认**：信号路径无法交互，且契约要求信号快速合作清理。
- **从图片内容反解尺寸与名称来恢复队列图片**：只能猜测；以发送数据为键保存
  原 `PendingAttachment` 才能保留完整 identity。
